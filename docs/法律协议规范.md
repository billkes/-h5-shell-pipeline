# 法律协议规范 (Legal Agreement Standard)

> **h5-shell-pipeline  canonical 路径**：本文件。Build Agent / PM 产包与 `verify_h5_legal_md` gate 均以此为准。

## 1. 核心目标
为 iOS 应用生成符合国际标准的隐私协议（Privacy Agreement）和用户协议（User Agreement），确保应用顺利通过 App Store 审核。

## 2. 全局强制要求 (Global Mandatory Requirements)
在生成任何风格的协议前，必须严格遵守以下底线：
*   **语言要求**：**全英文输出** (All content must be in English)。
*   **专业格式**：采用正式的法律文书排版，段落清晰。
*   **Markdown 正文排版（强制）**：
    *   **禁止** Markdown 表格（含 `| col |` 行及表头分隔行）。
    *   **禁止** Markdown 列表：无序（`-`、`*`、`+` 开头行）与有序（`1.`、`2.` 等数字加点开头行）。
    *   **允许** 标题层级：文档仅一个 `#`（H1，与文件名一致）；章节用 `##`、`###`；条款细节用正文段落承接，勿用列表代替。
    *   **正文** 使用普通段落：一句或一段一意，段与段之间空一行；并列要点须改写为连贯句子或分号连接的从句，**不得**用列表符号罗列。
    *   **禁止** 用引用块 `>` 批量罗列条款。
*   **头部日期**：协议正文头部必须标注最新更新日期：**Latest Updated: May 18, 2026**。
*   **地域规避**：严禁出现特定国家、地区及其相关法律体系字眼，保持国际化中立。
*   **年龄分级**：明确提及 App 年龄等级为 **18+**。
*   **内容安全机制**：
    *   在“Prohibited Conduct”或相关章节明确：Take action on reports of inappropriate content within **24 hours** (delete content and ban the user).
    *   提及应用内具备**filtering methods** for inappropriate content and a **user reporting mechanism**.
    *   表达对违规用户的 **Zero Tolerance** 态度。
*   **极简登录原则**：对于工具包，严禁编写 Login, Register, Logout 等复杂流程，强调 **Device Unique Identifier** 的唯一作用。
*   **底部联系方式**：协议正文底部必须增加 **Contact Us**，邮箱格式固定为：`{AppName}@gmail.com`。

## 3. 风格控制 (Style Control)
根据 task.csv **`协议风格`** 列（风格1 / 风格2 / 风格3）调整。请根据应用类型（通用包 vs 工具包）选择对应的风格模板。

## 4. 通用包风格 (General Pack Styles)

### A. 隐私协议 (Privacy Agreement)
*   **风格1 (Standard - 正式合规)**：
    *   **要求**：语言正式合规，段落字数不限。
    *   **低重复策略**：与旧协议特征重复度 <20%，优先采用新的条款逻辑和表述方式。
    *   **自查**：生成后需验证条款逻辑、案例举例与旧协议的重合部分不超过 15%。
*   **风格2 (Structured - 结构调整)**：
    *   **要求**：调整结构（如将“用户权利”提前至“信息收集规则”之前），采用更正式的表述。
    *   **创新点**：新增至少 1 个旧协议未涵盖的特色场景条款。
    *   **篇幅**：控制在 1000 字左右。
*   **风格3 (Concise - 简洁拆分)**：
    *   **要求**：拆分章节逻辑（如将“数据安全”拆分为“技术防护手段”和“管理流程规范”两章）。
    *   **创新点**：核心条款（收集范围、共享规则等）至少有 3 处实质性差异。
    *   **篇幅**：控制在 600 字左右。

### B. 用户协议 (User Agreement)
*   **风格1 (Standard - 完整合法)**：
    *   **要求**：内容完整合法，避免照搬市面常用模板，重新组织结构。
    *   **低重复策略**：与旧协议特征重复度 <20%，改写常规法律条款表述。
*   **风格2 (Formal - 模块重组)**：
    *   **要求**：涵盖账户注册、义务、版权、免责等基本模块，但避免高度重复。
    *   **创新点**：调整章节顺序，优先采用新的条款逻辑。
    *   **篇幅**：控制在 1000 字左右。
*   **风格3 (Innovative - 实质创新)**：
    *   **要求**：核心条款（权利义务、违约处理）有至少 3 处实质性创新。
    *   **创新点**：新增至少 2 个旧条款未涉及的具体场景说明。
    *   **篇幅**：控制在 600 字左右。

## 5. 工具包专属风格 (Tool Pack Specific Styles)

### A. 隐私协议 (Privacy Agreement)
*   **工具包风格1 (Minimalist Login - 极简登录)**：
    *   **核心**：仅获取设备唯一标识符用于登录验证，不收集任何个人信息。
    *   **重点**：说明设备号的使用目的、加密存储方式及注销删除规则。
    *   **篇幅**：1000 字左右，按逻辑模块分段输出。
*   **工具包风格2 (Feature Interaction - 功能交互)**：
    *   **核心**：包含功能服务使用、数据交互及个性化配置。
    *   **结构**：将“用户权利”前置，拆分“数据安全保障”。
    *   **创新点**：新增“工具功能合规适配条款”，明确用户对合规义务的配合。
    *   **篇幅**：800 字左右。
*   **工具包风格3 (No-PII Declaration - 无PII声明)**：
    *   **核心**：首章声明“无个人信息收集”，删除无关的个人信息处理章节。
    *   **差异点**：明确标识符仅本地存储、不关联个人信息、注销即删。
    *   **篇幅**：400 字左右，简洁正式的合规话术。

### B. 用户协议 (User Agreement)
*   **工具包风格1 (Device-ID Only - 设备ID专用)**：
    *   **核心**：开篇明确“设备标识登录即视为接受条款”，移除资料管理章节。
    *   **差异点**：补充设备标识使用限制及注销后清除规则。
    *   **特色条款**：增加“无个人信息场景下的服务责任界定”。
    *   **篇幅**：800 字左右，流程清晰。
*   **工具包风格2 (Quick Access - 快速访问)**：
    *   **核心**：以“服务全流程说明”（登录-使用-注销）开篇。
    *   **差异点**：明确自动生成标识、无需注册、一键注销流程。
    *   **特色条款**：增加“快速服务场景下的用户体验保障”。
    *   **篇幅**：700 字左右，通俗简洁。
*   **工具包风格3 (Global Compliance - 全球合规)**：
    *   **核心**：开篇列明 GDPR、CCPA 等法律依据，增设合规约束专章。
    *   **差异点**：明确标识符存储期限（如 180 天自动删除）及跨境使用合规说明。
    *   **篇幅**：800 字以内，严谨规范。

## 6. 命名与标题规范 (Naming & Title Convention)
1.  **文件命名**：
    *   隐私协议：`{主名字} Privacy Agreement.md`
    *   用户协议：`{主名字} User Agreement.md`
2.  **一级标题**：文档内部的一级标题（H1）必须与文件名保持一致（不含 `.md` 后缀）。
3.  **名称一致性**：`{主名字}` 必须与名称列表中提取的主名字完全一致。

## 7. Markdown 正文排版规范（输出物强制）

生成 `{主名字} Privacy Agreement.md` 与 `{主名字} User Agreement.md` 时，正文须符合法律文书阅读习惯，且便于 WebView / 文档平台渲染：

1.  **结构**：H1 标题 → 更新日期行（普通段落）→ `##` 章节 → 可选 `###` 小节 → 段落正文 → 文末 **Contact Us** 段落。
2.  **禁止表格**：不得出现任何 Markdown 表格语法；需对比或分项说明时，用段落叙述（例如「第一项……；第二项……」）。
3.  **禁止列表**：不得出现 `-`、`*`、`+` 或 `1.` 形式的列表行；枚举内容并入段落，用句号、分号或「此外」「同时」等衔接。
4.  **段落质量**：每段 2～5 句为宜，避免单句成段堆砌；关键数字与合规用语（18+、24 hours、Zero Tolerance 等）保留在段落内加粗即可。
5.  **生成后自查**：确认全文无 `|` 表格行、无列表行、无 `>` 引用块条款墙。

## 8. 撰写与执行规范
1.  **低重复验证**：在生成过程中，AI 需模拟自查步骤，确保新内容与历史协议特征的重复度低于 20%。

## 9. 流水线 Gate（h5-shell-pipeline）

`scripts/batch/h5_legal_md_gate.py` → `verify_h5_legal_md()` 在 **plan.gate** 阶段强制执行 §2、§6、§7 及 task.csv 协议风格篇幅下限。仅追加 `Children's Privacy` / `Limitation of Liability` 不足以通过。
